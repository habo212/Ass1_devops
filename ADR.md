# Architecture Decision Records

## 1. Backend framework: Python + Flask
Date: 2026-09-27
Status: Decided
Context: I need a small web backend that runs as one process, talks to SQLite and is easy to split into services later. Python is the language I'm most comfortable with, so I need to be able to explain every line.
Decision: Use Python with Flask and the built-in `sqlite3` module, organised with an app factory (`create_app`) so each feature domain can be registered separately.
Alternatives considered: Django: rejected because its admin, ORM and project structure are much more than a two-domain app needs, and it would add a lot of code I didn't write myself. FastAPI: a reasonable option, but async and Pydantic models don't buy me anything at this scale, and I know Flask better.
Consequences: Very little boilerplate, and the app starts in under a second. Flask doesn't give me validation or an ORM, so I have to write input checks and SQL myself.

## 2. Domain seam: records only talks to workouts through a two-function public interface
Date: 2026-09-30
Status: Decided
Context: The app has two domains, Workouts (logging sessions, exercises and sets) and Records & Progress (PRs, 1RM estimates, goals). Records needs workouts' sets to do anything, but it should be possible to move records into its own service later without rewriting it.
Decision: `gymlog/workouts/__init__.py` is the only thing other domains may import from workouts. It exposes `get_sets_for_exercise(name)` and `normalize_exercise_name(name)`, which return plain dicts and strings, never SQL rows or Flask objects. The dependency goes one way only: records imports workouts, never the other way round. Each domain has its own `service.py`, `repository.py`, `routes.py` and `schema.sql`.
Alternatives considered: Letting records write its own SQL joins over the workouts tables: less code, but then records depends on workouts' table layout and breaks on any schema change. Having workouts push new sets into records whenever a workout is saved: keeps PRs precomputed, but couples workouts to records in the other direction too, so neither could be split out alone.
Consequences: To split records out later, I only have to replace those two imported functions with HTTP calls to a workouts service (e.g. `GET /api/workouts/exercises/<name>/sets`). The cost is that records recomputes PRs from all sets on every request, which is fine for one person's log but would need caching at large scale.

## 3. SQLite schema: workouts → exercises → sets, records linked by exercise name
Date: 2026-09-28
Status: Decided
Context: A workout has several exercises and each exercise has several sets, and the records domain needs to find every set for one exercise to detect PRs. I also want the records domain to be splittable into its own service later, so its data can't be tightly tied to the workouts tables.
Decision: The workouts domain owns three tables, `workouts` 1→N `exercises` 1→N `sets`, joined by foreign keys with `ON DELETE CASCADE`. The records domain will own its own table and refer to exercises only by their name (plain text, no foreign key into the workouts tables).
Alternatives considered: One flat `sets` table with the date and exercise name on every row: simpler, but it repeats the date and notes on every set and can't represent "one visit" cleanly. A separate `exercise_types` lookup table with a foreign key from records: stricter, but it would chain the records tables to workouts tables, so they couldn't be moved into a different database later.
Consequences: Deleting a workout removes its exercises and sets automatically. Because records matches by name, the name must be normalised the same way everywhere ("bench press" = "Bench Press"), which the workouts service has to enforce.

## 4. Testing approach: pure service functions first, then routes on a temporary database
Date: 2026-10-01
Status: Decided
Context: The brief requires at least 70% coverage of the core business logic of both domains. Most of the real rules (input validation, name normalisation, PR detection, the Epley 1RM estimate) live in the two `service.py` files, while routes and repositories mostly pass data along.
Decision: Test every rule in `workouts/service.py` and `records/service.py` directly with plain Python values (using `pytest.mark.parametrize` for the bad inputs and a fixed `today` date), then add a smaller set of route tests through Flask's test client. A `conftest.py` fixture gives each test a fresh SQLite file in pytest's `tmp_path`, so the real SQL runs without touching `data/`.
Alternatives considered: Mocking the database in route tests: faster, but it would only prove the mocks work, not that my SQL and foreign keys do. Browser/end-to-end tests (e.g. Selenium): too heavy for the value they add here, and they would need extra packages.
Consequences: Coverage is 100%, and the SQLite schema (CHECK constraints, cascades) is exercised for real. The route tests are thinner: they cover the happy path plus 400/404 cases, not every combination, and there are no tests for concurrent writes because the app is single-user.

## 5. Not built: user accounts and login
Date: 2026-10-02
Status: Decided
Context: Gym Log is a personal training log, and the brief lets me decide whether to add authentication. Login would touch every table and every route, and the deadline is one week, so I had to decide early whether it was worth it.
Decision: No accounts or login. The app has one implicit user, and anyone who can reach the port can read and edit the log.
Alternatives considered: Flask-Login with hashed passwords and a `users` table: the standard approach, but it adds a `user_id` foreign key to `workouts` and `goals`, session handling, CSRF protection on every form and its own tests, roughly doubling the work for a feature that doesn't help the two domains I'm graded on. HTTP basic auth from an environment variable: much less code, but it would still be shared by everyone, so it protects the app without actually separating users.
Consequences: The app stays small and both domains could be finished and tested properly. Before the Azure deployment in Assignment 2, the app must not be left publicly reachable without at least network restrictions, and adding real users later means adding `user_id` to the `workouts` and `goals` tables.

## 6. The split: records calls workouts over HTTP for an exercise's sets
Date: 2026-11-16
Status: Decided
Context: Assignment 2 turns the monolith into two services, each with its own process and its own data. In the monolith, records imported two functions from workouts (ADR-2): `get_sets_for_exercise` to read the sets, and `normalize_exercise_name` to clean names. An import can't cross two processes, so both had to be replaced.
Decision: The seam stays exactly where ADR-2 put it. Workouts owns `workouts`, `exercises` and `sets`; records owns `goals`. One thing crosses the seam, in one direction: records calls `GET /api/workouts/exercises/<name>/sets` on workouts (in `records/workouts_client.py`), finding it through the `WORKOUTS_URL` environment variable and waiting at most `WORKOUTS_TIMEOUT_S` seconds (default 2). The call happens server side, inside records, because the PR and 1RM maths live in records and need the raw sets. If workouts can't be reached, times out or answers with an error, `GET /api/records/<name>` returns 503 with a clear message and still includes the goal, which is records' own data. Setting and deleting goals never calls workouts. Workouts never calls records.
Alternatives considered: Having the browser fetch the sets from workouts and post them to records: no server-to-server call, but the records logic would then trust whatever sets the browser sends, and the brief needs one flow that crosses the seam server side. Caching the last sets in records so PRs still show when workouts is down: nicer for the user, but it means a second copy of the sets that can be stale after a workout is edited or deleted, and more code than a personal log needs. Retrying the call: a workout log that is down stays down for longer than a retry, so it would only make the failure slower.
Consequences: ADR-2 held: only `summary.py` changed how it gets sets, and the service logic in both domains is untouched. The second imported function couldn't become a call without making goals depend on workouts being up, so the name-cleaning rule is now copied into `records/service.py`. If the rule changes in one service and not the other, goals would stop matching their exercises, so a test in each service pins the same examples. Every records page now costs one HTTP request, and records is only as available as workouts for PRs, but each service still serves its own data when the other is stopped.

## 7. Data and migrations: one SQL Server database per service, changed only by numbered migrations
Date: 2026-11-17
Status: Decided
Context: The monolith kept every table in one SQLite file and created them with `CREATE TABLE IF NOT EXISTS` on each start (ADR-3). After the split each service needs its own database, the brief requires SQL Server (Azure SQL serverless in production), and once a database holds real data its schema must be changed in place, never recreated.
Decision: Each table moved to the service that owns it: `workouts`, `exercises` and `sets` to the `workouts` database, `goals` to the `records` database. The SQL was ported to T-SQL (`INT IDENTITY`, `NVARCHAR`, `DATE`, `FLOAT`, `OUTPUT INSERTED.id`, update-then-insert instead of `ON CONFLICT`), and the local SQLite data was not copied over because it was only test data. Each service logs in with its own SQL login that is a user in its own database only, so it physically can't read the other one. The schema is defined by numbered files in `services/<name>/migrations/`, applied on startup by a small runner of my own (`migrate.py`): it records each applied file in `schema_migrations`, runs each file in one transaction, splits files on `GO` lines, and never re-runs a file. Locally, `db/init.sql` (run by a one-off compose service) creates the databases and logins. Its passwords, like the ones in `docker-compose.yml`, are local-only defaults that can be overridden, so the stack starts from a clean clone. SQL Server is bound to 127.0.0.1 and holds nothing real. The Azure passwords exist only as GitHub secrets.
Alternatives considered: Alembic: well tested and can autogenerate migrations, but it is built around SQLAlchemy, which this project doesn't use, and it would hide the part I have to be able to explain. Keeping `IF NOT EXISTS` scripts: they can create tables but can't change a table that already holds data. One shared login for both databases: simpler, but then nothing stops one service reading the other's tables, which is what the split is meant to prevent.
Consequences: Integrity lost at the seam: `goals.exercise_name` and the `set_id` values records receives point into a database records can't check, and deleting the last workout of an exercise leaves its goal behind. This is compensated in code: both services clean names with the same rule, records answers 404 when an exercise has no sets, and a leftover goal reappears if the exercise is logged again. Recovery plan for a bad migration in production: a migration that fails is rolled back by its transaction and not recorded, so the container fails to start and the previous revision keeps serving. A migration that succeeds but is wrong is never edited; the fix is a new numbered migration. If it destroyed data, Azure SQL point-in-time restore (7 days of backups) restores the database as a copy from before the deploy, and the lost rows are copied back. Because rolling back the image doesn't roll back the schema, every migration has to keep working with the previous image too (add columns with defaults, and remove things only in a later migration).

## 8. Deployment: Azure Container Apps scaled to zero, a free serverless database each, and a pipeline that signs in without a password
Date: 2026-11-21
Status: Decided
Context: The system has to run on Azure from my own Azure for Students subscription ($100 of credit for 12 months), which only allows five European regions. CD must deploy only from `main`, the two services must stay as separate deployables with separate databases (ADR-6, ADR-7), and no credential may live in the repository.
Decision: Every Azure resource is created once by `infra/azure-setup.sh`, a re-runnable script, in `rg-sdd-3a` in Germany West Central: the SQL server `hrahal-ieu2024-sql`, one database per service on the free serverless offer (auto-pauses after an hour idle, and stops instead of charging when the free allowance runs out), one Container App per service (Consumption plan, 0–1 replicas, 0.25 vCPU) and the Static Web App `hrahal-ieu2024-ui`. Each service connects as a contained database user (`db/azure-user.sql`) that owns only its own database, the Azure version of the local logins. Their passwords are generated by the script and stored as Container App secrets on Azure and in `~/.config/gymlog-azure` on my laptop, not in GitHub, which corrects what ADR-7 planned: the pipeline never needs them, because it only changes the image. The pipeline runs on push to `main` after every test, integration and build job has passed. It pushes both images to GHCR tagged with the commit SHA, updates both Container Apps, writes `ui/config.js` with the services' real URLs, uploads the UI, and polls both `/health` endpoints until they report that SHA. It signs in to Azure as the managed identity `hrahal-ieu2024-github` through GitHub OIDC. Azure trusts only tokens for `refs/heads/main` of this repository, the identity is Contributor on the resource group only, and the three GitHub secrets it uses are IDs, not passwords.
Alternatives considered: A service principal with a client secret: the usual tutorial setup, but the secret is a long-lived password in GitHub that has to be rotated. Azure Container Registry: keeps images inside Azure, but costs money every day while GHCR is free for a public repository. Bicep or Terraform: real infrastructure as code, but another language to learn for a handful of resources created once; the script is readable top to bottom. Always-on replicas and a provisioned database: no cold start, but they would use up the student credit.
Consequences: The first request after a quiet period is slow: the Container App starts from zero and the database may need about a minute to resume. The connect retry from ADR-7 and a 30-second, 30-attempt health check in CD cover this, but a user can see a slow first page. Rolling back means re-running the pipeline for an older commit, because every image is kept under its SHA. If the free database allowance runs out, the databases pause until next month rather than costing money, so the demo would be down instead of billing me.
